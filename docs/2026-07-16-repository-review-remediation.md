# Repository Review Remediation Plan

**Date:** 2026-07-16
**Review basis:** `e08d353` (`main`)
**Status:** Accepted decisions and implementation record
**Scope:** Worker API, Workers Cache behavior, R2 lifecycle, demo, deployment,
documentation, tests, repository governance, and the portable-deployment draft.

The active ingestion/language workstream is intentionally excluded from this

## Decisions recorded on 2026-07-16

| ID | Decision / status |
|---|---|
| API-02 | Resolved by removal (2026-07-17): the `/namespaces` prefix registry, the `namespaces` cache tag, and the unused per-namespace `labels:{ns}` label tag were deleted rather than reframed. The service now speaks only absolute IRIs; prefix/CURIE expansion is a client-side concern with no server surface. The demo no longer shows a "served" prefix panel. This supersedes the reframe recommendation in the findings table below. |
| CACHE-01 | Revised (2026-07-16): labels now use a split TTL - `max-age=3600` for browsers, `s-maxage=31536000` for the edge. A purge clears the Cloudflare edge; browsers cannot be purged but refresh within the hour. Only the versioned context document keeps one-year `immutable` browser caching. |
| CACHE-02 | Implement strict query validation now. Do not introduce a canonical redirect or path form yet; parameter ordering remains a documented cache-key limitation. |
| DATA-01 | Deferred. The intentionally simple future refresh model is wipe-and-rewrite. Until that is designed, live-keyspace partial-write and stale-key risks remain accepted and documented. |
| DEMO-02 | Deferred. Existing performance claims require a repeatable benchmark before they are changed or substantiated. |
| OPS-01 | Deferred. No observability or health-endpoint architecture was introduced in this change. |
| PORTABLE-01 | Parked. Cloudflare remains the supported architecture; Azure/AWS portability is not being pursued now. The existing portable draft is retained untouched for later reassessment. |

## Priorities

| Priority | Meaning |
|---|---|
| **P0** | Correctness or production-readiness issue that should block recommending the service for general use. |
| **P1** | Important reliability, cost, API, or product-trust issue to address before the next stable release. |
| **P2** | Maintainability, documentation, testing, or governance improvement that should follow the correctness work. |

## Issue and remediation matrix

| ID | Priority | Area | Issue and evidence | Proposed solution | Acceptance criteria |
|---|---|---|---|---|---|
| CACHE-01 | **P0** | Browser cache invalidation | Label responses used `public, max-age=31536000, immutable` (`src/lib/cache.ts`). An edge purge cannot invalidate a response already stored in a browser. | **Revised policy (2026-07-16):** split the TTL - `max-age=3600` for browsers, `s-maxage=31536000` for the edge. Purges keep clearing the edge immediately; browser-held entries age out within the hour, so data refreshes reach returning visitors without URL versioning. The versioned context document keeps the one-year `immutable` directive because its content never changes at its URL. | An edge purge plus a one-hour browser window bounds staleness. No promise is made that an edge purge invalidates a browser cache. |
| API-01 | **P0** | Cross-origin API access | Normal self-hosted deployments are API-only, but responses have no `Access-Control-Allow-Origin`. `OPTIONS` is rejected by the GET-only guard in `src/index.ts`. Browser examples in `docs/consuming.md` therefore work only when the app and API share an origin, as the maintainer demo does. | For the public read-only routes, return `Access-Control-Allow-Origin: *`, support `OPTIONS`, and allow `GET, HEAD, OPTIONS`. Do not enable CORS on `/admin/*` or `/dev/*`. If deployments later support restricted origins, make the allowlist explicit and emit `Vary: Origin` only when reflecting an origin. | A browser hosted on another origin can read `/label`, `/namespaces`, and the context document. Preflight and `HEAD` behavior are tested. Admin and development routes do not acquire permissive CORS headers. |
| CACHE-02 | **P0** | Cache-key fragmentation and denial of wallet | Workers Cache keys on the full request URL, while `src/routes/label.ts` formerly ignored unknown query parameters. | Implement immediate validation before R2: exactly one `iri`, at most one `lang`, no unknown parameters, bounded values, and a valid absolute HTTP(S) IRI. Do not add a redirect or canonical path form now. Parameter ordering remains a known fragmentation limitation. | Unknown or duplicated parameters never reach R2. Tests cover unknown, repeated, invalid, and literal-percent values. |
| CACHE-03 | **P0** | Data-refresh purge | `PURGE_TOKEN` is optional in scripts and deployment instructions, although skipping purge can leave edge entries fresh for one year. Scripts currently describe this as normal TTL expiry without making the one-year consequence clear. | Add a `just purge-token-init` flow that generates a cryptographically random token, installs it with `wrangler secret put`, and records the local/CI half in the documented secret store. Make cache purge mandatory and fatal after a successful production data refresh. Retain a bounded CDN TTL as a safety net even when purge fails. Code deployments do not require a full purge while Workers Cache uses its default version-isolated cache. | A documented fresh deployment can configure purge without manual guesswork. Production seeding fails visibly if invalidation cannot be applied. No script reports success after uploading data that the edge will continue hiding. |
| COST-01 | **P1** | Billing and cost model | `docs/architecture.md` estimates 50M monthly requests at about $1.50 and 500M at about $15. Workers Cache hits avoid Worker CPU and R2 reads, but they are still billed as Worker requests. The demo also mixes Free and Paid plan statements without the Paid plan base charge and included requests. | Recalculate examples from the current Cloudflare pricing model: account base charge, included requests, request overage, CPU, R2 Class B operations on cache misses, storage, and egress. State the pricing date and link the official source. Keep measured traffic assumptions separate from platform prices. Add a small calculator or formula rather than hard-coded optimistic totals. | Every published total can be reproduced from a stated formula and current official prices. Cache hits are described as CPU/R2 savings, not free requests. Free-plan and Paid-plan examples are clearly separated. |
| API-02 | **P1** | Namespace API semantics | `GET /namespaces/{prefix}` reads `namespaces/{prefix}/all.json`, but no pipeline writes those objects and `docs/architecture.md` explicitly says namespace dumps are omitted. `/namespaces` returns a static prefix map, not namespaces actually present in R2, while the demo labels those entries as “served”. | Choose one contract. The simplest option is to remove the detail route and define the collection endpoint as a static prefix registry, preferably `/.well-known/prefixes` or `/prefixes`. If store coverage is required, generate a deployment manifest containing namespace, term count, languages, source, and refresh time, and serve details from that manifest. Do not infer availability from the static prefix map. | No advertised endpoint is permanently unreachable. The API and demo distinguish “known prefix” from “data present in this deployment”. README, route tests, and live smoke tests agree on the contract. |
| API-03 | **P1** | IRI decoding and validation | `URLSearchParams.get("iri")` already percent-decodes the value, after which `decodeURIComponent()` decodes it a second time. IRIs containing valid percent-escaped components can therefore map to the wrong R2 key. Non-absolute or oversized values are also accepted until a downstream failure. | Remove the second decode. Treat the `URLSearchParams` value as the IRI, validate it as an absolute `http:` or `https:` IRI if those are the supported schemes, and enforce an explicit byte limit compatible with R2 keys and the public API. Preserve percent escapes exactly as supplied by the decoded query value. | Tests cover fragments, Unicode, literal percent escapes, encoded slashes, plus signs, malformed input, unsupported schemes, and maximum length. The key used at read time exactly matches the key produced by the uploader. |
| DEMO-01 | **P1** | Landing-page demo truthfulness | `demo/public/demo-widget.js` contains a hard-coded IRI-to-label table, fixed synthetic latency values, and an unconditional `HIT` badge. The landing page calls this “live” and says each IRI fires an edge-cached GET. The separate `/demo` playground does make real requests. | Prefer making the widget genuinely live: resolve its fixed IRIs with `Promise.all`, display the actual HTTP status, measure elapsed client time, and show `Cf-Cache-Status` only if it is exposed and available. Otherwise label the widget clearly as an illustration and remove synthetic network and latency claims. Keep the real playground as the proof surface. | Browser network tools show the requests represented by the widget, or the UI explicitly says no requests are made. It never displays fabricated cache status or latency as observed data. |
| DATA-01 | **P1** | Data refresh consistency and deletion | Uploads still write concurrently into the live keyspace. Removed source terms remain and a failed upload can expose a mixed generation after purge. | **Deferred / accepted risk.** Keep the eventual KISS model as explicit wipe-and-rewrite until scale justifies generations and atomic cutover. Do not advertise atomic refresh or deletion today. | The risk and deferred design are documented. No partial implementation implies atomicity. |
| DATA-02 | **P1** | Versioned JSON-LD context | The architecture says `context/labels-v1.json` must never change, but every ingest emits it and every upload overwrites it. A context edit can silently change the meaning of already cached label documents while retaining the `v1` URL. | Treat contexts as immutable artifacts. During upload, allow an existing versioned context only when its bytes/hash match. Fail on a mismatch and require a new path such as `labels-v2.json`, followed by regeneration of documents that reference it. Record the context version in the seed manifest. | Re-running an unchanged seed is idempotent. Changing a v1 context causes a clear failure. A documented v2 procedure updates references without mutating v1. |
| DOCS-01 | **P1** | Documentation drift | The architecture and deployment guides contain conflicting key layouts, cache TTLs, cache-tag names, compression behavior, response shapes, supported-data claims, and Workers Cache status. `docs/DEPLOY.md` says Workers Cache is not enabled even though both Wrangler configs enable it. Public bucket and release-tarball bootstrap paths are described but not implemented. | Make README and `docs/DEPLOY.md` operational truth, keep `docs/architecture.md` current-state architecture, and retain historical decisions only as dated ADR/migration documents. Remove or mark unimplemented distribution channels. Add a documentation check that compares important literals against configuration/source: TTLs, route names, bucket naming, and key examples. | A new user can follow one path from clone to a successful lookup without encountering contradictory commands or nonexistent artifacts. Search finds only one current key layout and cache policy. Historical documents are clearly labeled historical. |
| DEMO-02 | **P1** | Unsupported performance claims | The live landing page claims `<50ms` for 95% of users, while `docs/FAQ.md` says performance characteristics are reasoned rather than measured. Region count, concurrency guidance, and hit-rate statements are also presented more confidently than the evidence supports. | Remove percentile claims until a repeatable benchmark exists. Define a benchmark matrix covering warm/cold cache, representative regions, response sizes, HTTP versions, and R2 misses. Publish the collection date, tooling, sample size, and raw summary. Phrase unmeasured expectations as design goals. | Every percentile or hit-rate claim links to a reproducible benchmark. Marketing and technical documentation use the same measured numbers and date. |
| TEST-01 | **P1** | Test coverage and CI gates | The Worker route suite passes, but it does not cover CORS, percent-preserving IRI behavior, strict query validation, cache-control separation, real cache invalidation, demo behavior, deployment recipes, or documentation consistency. Workers Cache itself is absent from local emulation, so the purge test only verifies the HTTP wrapper. | Add unit/runtime tests for API edge cases and headers; browser tests for landing/playground behavior; script tests using temporary manifests and mocked S3; `wrangler deploy --dry-run`; shell linting; HTML/JS syntax checks; and a deployed smoke test in staging for `MISS -> HIT -> purge -> MISS`. Keep platform-dependent tests separate from fast PR tests. | CI prevents regressions in every P0/P1 behavior above. The staging test proves the actual Cloudflare cache lifecycle rather than only mocked handler output. Demo JavaScript and deployment configuration are validated on every PR. |
| OPS-01 | **P1** | Observability and failure handling | Wrangler configuration does not enable observability, handlers do not emit structured logs, and R2 failures fall through as generic platform errors. There is no explicit health/readiness signal or request correlation. | Enable Workers observability with a deliberate sampling rate. Emit structured events for route, status, cache-relevant rejection reason, R2 outcome, and request ID without logging secrets or full sensitive IRIs. Return stable JSON error envelopes for expected storage failures. Add an uncached shallow health route and, if needed, a separate readiness check that verifies the required context object. | Operators can distinguish cache hit traffic, validation rejection, R2 miss, R2 failure, and purge failure. Alerts and a minimal runbook exist. Health endpoints cannot be mistaken for proof that label data is fully populated. |
| DEPLOY-01 | **P2** | Deployment ergonomics | `just` is central to the deployment path but is absent from prerequisites. `bootstrap` uses `bucket || true`, suppressing authentication, networking, and permission failures as well as “already exists”. Configuration is generated by broad text substitution, and staging/production separation is described but not implemented. | Document and check the required `just` version, while keeping a complete raw Wrangler path. Replace `|| true` with an explicit existence check or narrowly handle the known “already exists” result. Prefer a checked template or Wrangler environment configuration over unconstrained `sed`. Add distinct staging and production buckets/configuration before automated promotion. | Missing tools fail with an actionable message. Bucket creation reports real failures. Generated configuration is validated by Wrangler, cannot silently target the wrong bucket, and supports a tested staging-to-production flow. |
| GOV-01 | **P2** | Repository governance and supply chain | The repository invites reuse and contributions but has no `LICENSE` or `SECURITY.md`. `package.json` has no Node engine constraint. GitHub Actions use mutable major-version tags rather than immutable commit SHAs. | Choose and add a license, add a security-reporting policy and supported-version statement, declare the Node engine, and document release support. Pin third-party Actions to reviewed commit SHAs with version comments and let Dependabot maintain them. Add CODEOWNERS/branch protection if multiple maintainers are expected. | Users can determine their legal rights and how to report vulnerabilities. Unsupported Node versions fail early. CI dependencies are reproducible and reviewable. |
| RELEASE-01 | **P2** | Release and commit history | Five releases were cut in a few days, repeated feature-branch merges produced duplicate changelog entries, and tag/package naming is transitioning from `rdf-label-resolver` to `rdf-label-cache`. This obscures which change shipped once and complicates future automation. | Adopt one merge policy for conventional commits, preferably squash merges with a release-relevant PR title. De-duplicate the changelog in the next release, document the tag-name transition, and add a release checklist that verifies package name, tag prefix, links, demo deployment, and data compatibility. | Each merged PR contributes one intended changelog entry. New tags use one documented naming scheme. Release notes and compare links identify the actual shipped commits without duplicates. |
| PORTABLE-01 | **P2** | Portable-deployment draft | `docs/portable-deployment-design.md` treats `ctx.waitUntil` write-behind as portable, maps full IRI keys directly onto a filesystem, calls the Azure Functions adapter first-party, and defines storage interfaces without streaming, metadata, conditional writes, deletion, generation management, or background-work semantics. These differences prevent the claimed identical behavior across runtimes. | Introduce explicit portable contracts: safe reversible or hashed filesystem key encoding; a `BackgroundTasks` abstraction whose guarantees are defined per runtime; streaming `BlobStore` reads/writes with metadata and conditional operations; generation/list/delete support; and contract tests shared by R2, filesystem, S3, and Azure drivers. Describe the Azure adapter accurately as third-party and evaluate it as a dependency. Keep CDN invalidation and authentication as platform adapters, not implied core behavior. | The same conformance suite passes for every supported driver/runtime. A response is never acknowledged before required durable work unless the runtime guarantees background completion. Hostile IRIs cannot escape the filesystem root or collide through case/path normalization. Portability claims list known semantic differences. |

## Recommended implementation order

1. **Correct the public read path:** CACHE-01, API-01, CACHE-02, and API-03.
2. **Make refreshes safe:** CACHE-03, DATA-01, and DATA-02.
3. **Make the published product accurate:** COST-01, API-02, DEMO-01, DOCS-01, and DEMO-02.
4. **Add production evidence and operations:** TEST-01 and OPS-01.
5. **Harden adoption and maintenance:** DEPLOY-01, GOV-01, and RELEASE-01.
6. **Resume portability work only after the core contracts stabilize:** PORTABLE-01.

## Suggested release gates

### Before the next stable release

- All P0 items are complete.
- Production refresh either cuts over atomically or demonstrably cannot expose a
  partial upload.
- Browser and edge cache lifetimes are separately tested.
- Cross-origin consumption works from a separate test origin.
- Current documentation contains no unimplemented bootstrap artifact or dead API
  route.

### Before advertising production readiness

- The deployed `MISS -> HIT -> purge -> MISS` lifecycle is tested automatically.
- Cost and latency claims are dated, reproducible, and sourced.
- Observability and failure runbooks exist.
- A license and security policy are present.
- Data rollback and stale-key removal have been exercised in staging.
